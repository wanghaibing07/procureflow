# ProcureFlow：采购补货协同助手

给采购员和审批人用的可复现演示。采购员查缺货和供应商报价、生成草案，审批人确认后提交到独立的模拟 ERP，拿到可追踪的回执。库存、价格和供应商均为合成数据。

## 项目故事

**业务问题：**采购员要同时核对现有库存、预留、在途、预测需求和供应商交期，才能判断需要补多少、找谁买。系统把这些数据汇总成可解释的采购建议，并把下单动作留给审批人。

**关键取舍：**模型负责理解请求、查询和解释，不直接创建、审批或提交草案。采购员选择物料并确认服务端预览后才建单；数量、金额和供应商排序由确定性规则计算，界面展示数据库中的草案明细。模拟 ERP 用草案编号去重，避免请求超时重试时重复受理。

**实际排障：**一次审查发现建单成功但响应丢失后，如果库存已变化，同一个请求重试可能拿不到原草案。现在按采购员、幂等键和原始请求保存意图，再根据意图返回原单；SQLite 与 MySQL 的并发重试都有测试。接入真实模型时还发现服务一次返回多个工具调用，已增加受限顺序处理和数量上限。首次容器部署还发现严格 `umask 077` 下源码对非 root 用户不可读，已在镜像构建时规范源码权限并重验。

## 运行

需要 Docker Compose 和 Python 3.12。在项目目录运行：

```bash
python scripts/demo_env.py
docker compose up --build
```

打开 [采购工作台](http://127.0.0.1:8000)，使用 `.env` 中的 `PROCUREFLOW_BUYER_TOKEN` 和 `PROCUREFLOW_APPROVER_TOKEN` 切换身份。令牌生成脚本只创建本地 `.env`，不会覆盖已有配置；模拟 ERP 和 MySQL 端口不映射到宿主机。POSIX 系统上新建的 `.env` 仅授予文件所有者读写权限；Windows 上文件继承所在目录的 ACL，应确保目录只允许获授权的本机用户访问。

没有 Docker 时，安装 uv 并运行令牌生成脚本，然后在两个终端分别启动 HTTP 服务。此路径默认使用两个独立 SQLite 文件：

```bash
uv sync --locked
uv run --locked --env-file .env uvicorn procureflow.mock_erp:app --port 9001
uv run --locked --env-file .env uvicorn procureflow.api:app --port 8000
```

## 演示路径

[观看 33 秒采购流程演示](demo/procureflow-synthetic-demo.mp4)（基于 `2120df5`，查询等待片段已加速）。

1. 以采购员身份登录，查看 `2026-01-01` 起未来 7 天的数据。`BRACKET` 缺 20 件，系统选出的 `S-FAST` 报价供货周期为 4 天，符合计划窗口，金额为 230.00；`GASKET` 缺 23 件，现有报价的供货周期超过该窗口。这些是演示报价中的参考周期，并非供应商的实际交付承诺。
2. 勾选 `BRACKET`，点「查看采购预览」，核对物料、供应商、数量、单价和合计；再点「确认并生成草案」，核对持久化后的草案明细。采购员没有审批和提交权限。
3. 切换到审批人，审批通过，再点「提交至模拟 ERP」。检查回执和三条审计事件。通过 API 重试同一采购单会得到同一个回执。

库存和报价规则在 Python 中执行。模拟 ERP 根据采购单 ID 持久去重；如果提交请求超时，审批人可重试同一草案。业务库和模拟 ERP 回执分开存储。

每次预览带有一次性确认凭据，有效期为 15 分钟。确认时服务端会核对采购员、所选物料、计划时间及当前采购明细；价格、数量或供应商方案变化、预览过期时，需要重新预览并确认。已成功提交的同一确认请求即使随后库存变化也可以重试找回；同一预览不能换一个请求编号再次建单。

如果确认后浏览器没有收到结果，在同一浏览器重新登录相同采购员，使用「待确认结果的请求」中的「找回或完成上次草案」。该操作会使用原请求：如果先前已提交则找回原单，如果尚未提交且原预览仍有效则可能完成建单。要解除待定请求时，页面会先请求服务器撤销预览；若原请求已提交，服务器返回已有草案供核对。网络错误或撤销结果不明时，页面保留待定记录，不应仅凭本地清除认定服务器操作已取消。清除站点数据或换设备会丢失浏览器记录，先检查已有草案，再决定是否新建。若看到「发现旧版未确认结果的请求」，先核对草案列表，再确认已核对；旧版记录保留在浏览器中，不会自动变成新单。

## 可选模型

要启用自然语言输入，在本地 `.env` 增加 `PROCUREFLOW_MODEL_URL`、`PROCUREFLOW_MODEL_API_KEY`、`PROCUREFLOW_MODEL_NAME`，重启应用。URL 填模型服务的 Chat Completions 基础地址（如以 `/v1` 结尾），模型必须支持函数工具调用。工具仅处理本演示的合成数据。

单次模型请求默认超时为 20 秒；较慢的模型可在 `.env` 中设置 `PROCUREFLOW_MODEL_TIMEOUT_SECONDS` 为 1–180 的整数，例如 `90`，再重启应用。连接超时仍为 5 秒；这是每次 HTTP 请求的超时配置，并非整次多轮工具调用的总时限。超时会返回 504，增加时间不保证模型调用成功或回答正确。未配置模型时忽略此选项，不影响手工采购。

使用 Compose 时，模型地址必须从应用容器内可达；`127.0.0.1` 指向容器自身，不能直接访问宿主机上的 Magpie。非回环地址必须使用 HTTPS，并保持证书验证；若模型服务只监听宿主机回环地址，需先确认适合当前环境的受控连接方式及证书信任，再配置容器可达的地址。不要将密钥放进仓库或演示记录。旧版 Compose 与宿主机 Magpie 的组合未验收。

模型可以查库存、报价和补货建议，不能调用建单、审批或提交工具。采购员在建议列表明确选择物料并确认预览；审批和提交由审批人分别操作。页面将服务端固定业务规则与模型回答分开展示；模型仍可能出错，应以系统规则和已持久化的草案明细为准。工具调用轨迹可在界面查看；数据库保存模型、步骤、用量等精简记录，不记录提示词和答复全文。

## 状态与排障

- `GET /healthz` 检查应用进程是否存活，并返回是否配置模型；它不代表数据库就绪。`GET /readyz` 检查数据库连接和已映射的表、字段；成功为 HTTP 200，不可用时为 503。它不检查真实模型回答质量或模拟 ERP 的可用性。
- 页面提示预览冲突时，先核对已有草案并使用页面的服务器撤销或找回流程；只有结果明确后才重新选择物料、查看预览并确认。不要反复使用其他请求编号提交同一份预览。
- 旧客户端的 `allow_draft=true` 不能再用来启动模型建单；已完成且原请求绑定可核对的旧单允许只读找回，无法核对时返回冲突并提示检查草案列表。使用新接口应先调用 `POST /api/drafts/preview`，再携带所选物料、计划窗口、`preview_hash` 和 `Idempotency-Key` 调用 `POST /api/drafts`。不要公开预览凭据或演示令牌。
- 模型未配置或不可用时，采购员仍可按页面建议手动预览和建单。模拟 ERP 不可用时，先检查服务，已审批草案可稍后重试提交；不要仅凭超时认定 ERP 未受理。
- 数据库结构由应用启动时创建；本演示没有完整的生产数据库迁移工具。升级或清理数据前先按环境需要备份并确认范围，不要对真实业务库运行演示数据。

## 验收

在已经启动、只包含合成演示数据的隔离环境中，可以运行以下本机 API 验收。脚本读取本地令牌但不输出令牌；它会创建并提交一张新的演示草案，并验证角色权限、重试、模拟 ERP 回执和审计事件。不要针对真实业务环境运行。

```bash
python scripts/verify_compose.py --base-url http://127.0.0.1:8000 --env-file .env --synthetic-demo
```

```bash
uv run --locked pytest -q
```

默认使用本地 SQLite 和模拟模型输入。要追加 MySQL 验收，设置 `PROCUREFLOW_TEST_DB_URL` 为独立的 `procureflow_test` 数据库连接，再运行 `uv run --locked pytest -q tests/test_api.py tests/test_agent.py`；测试只接受数据库名严格等于 `procureflow_test` 的 MySQL 地址，并使用唯一请求和采购员数据。测试覆盖未审批的提交、采购员越权、同一草案重放、模型请求并发和 ERP 回执。真实模型应另外核对工具调用、草案参数和最终结果；模拟测试不计入真实模型成功率。

如果已安装 ego-browser，可运行下面的浏览器测试；将示例中的文件 URL 换成该测试文件的实际绝对路径。测试使用本地合成的模拟服务，验证建单响应中断后的刷新重试，不需要真实模型或数据库：

```bash
ego-browser nodejs -e "await import('file:///ABSOLUTE/PATH/TO/procureflow/tests/browser_retry.mjs')"
```

同目录的 `browser_retry_real.mjs` 使用项目虚拟环境启动真实 API、独立临时 SQLite 和本机模拟模型，模拟确认草案及模型查询的响应丢失，检查刷新后的恢复。它不调用真实模型；复跑时按上面的方式将文件名替换为 `browser_retry_real.mjs`。

配置真实模型并启动独立演示环境后，可运行原 15 条固定场景及 10 条补充负面场景；此操作会发起模型请求，可能产生费用，并创建两张合成采购草案，仅针对合成数据和本地演示服务。先通过安全的终端环境设置 `PROCUREFLOW_BUYER_TOKEN` 和 `PROCUREFLOW_APPROVER_TOKEN`，然后执行：

```bash
uv run --locked python scripts/evaluate_agent.py --base-url http://127.0.0.1:8000 --output evaluation.json --run-live
```

结果文件不得已存在。检查范围包括工具调用、草案内容和未授权写入；模型回答需逐条复核。旧基准包含旧版模型辅助建单，不能直接与当前流程的结果比较。

### 演示与交接检查

可按以下步骤检查：

1. 按运行说明启动演示，以采购员身份查询缺口、选择 `BRACKET`，核对预览并确认；以审批人身份复核草案、审批并提交模拟 ERP，核对回执和审计。
2. 记录所用提交版本、环境、复现步骤及实际结果；尝试预览失效或响应中断恢复，并保存不含凭据的必要证据。可录制一段目标为三分钟内的演示。
3. 评估效果时，对相同采购任务分别记录人工操作与 Agent 辅助流程的耗时、错误与修改次数、Token 消耗和实际可核算费用；未取得的数据标为待测。
